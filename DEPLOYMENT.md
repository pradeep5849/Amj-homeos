# AMJ HomeOS deployment runbook

This runbook deploys the verified Stage 11 server application. It does not turn AMJ HomeOS into a static site and does not configure hardware or notification providers.

## Runtime inventory

| Requirement | Production value |
|---|---|
| Runtime | Node.js `>=20.9.0 <25`; select Hostinger Node.js **22.x** |
| Install | `npm ci` |
| Build | `npm run deploy:build` |
| Start | `npm start` (runs `next start`) |
| Database | Persistent external PostgreSQL reachable over TLS from the app |
| Prisma client | Generated by `npm run deploy:build` |
| Production migrations | `npx prisma migrate deploy` (included in `npm run deploy:build`) |
| Local file persistence | None; application state and sessions persist in PostgreSQL |
| Liveness URL | `GET /sign-in` must return `200` |

`next start` reads the platform-provided `PORT` and binds to `0.0.0.0` by default. Do not set a hard-coded port. `/sign-in` proves that the Next.js process and routing are live without requiring authentication; after deployment, also sign in and open `/api/v1/auth/me` in the same browser to verify database-backed readiness.

## Environment variables

Enter secrets in **hPanel → Node.js application → Environment Variables**. Never upload a populated `.env` file.

### Required on every build and runtime

| Name | Requirement |
|---|---|
| `DATABASE_URL` | A PostgreSQL connection URI beginning `postgresql://`. Require TLS according to the database provider, commonly with `?sslmode=require` (or `&sslmode=require` when the URI already has a query). Use the provider's pooled/runtime URI only if it supports Prisma transactions and migrations; otherwise use its direct URI for deployment migrations. |
| `SESSION_SECRET` | A cryptographically random value of at least 32 characters. Generate outside Hostinger, for example `openssl rand -base64 48`; paste only the output into hPanel. Keep it stable for the deployment. |
| `NODE_ENV` | `production`. This enables HTTPS-only session cookies and keeps test providers disabled. |

Hostinger supplies `PORT`; do not add it manually unless hPanel specifically instructs you to do so.

### Optional or one-time only

| Name | When used |
|---|---|
| `MOBILE_TOKEN_ENCRYPTION_KEY` | Only when accepting mobile push-token registrations. It must be exactly 32 random bytes encoded as base64 (`openssl rand -base64 32`). Push delivery remains `NOT_CONFIGURED`; omit this for the temporary browser test. |
| `SUPER_ADMIN_EMAIL` | One-time `npm run bootstrap` input only. Do not retain it in runtime variables after bootstrap. |
| `SUPER_ADMIN_PASSWORD` | One-time bootstrap password, at least 12 characters. Remove it immediately afterward. |
| `SUPER_ADMIN_NAME` | One-time bootstrap display name. |

`DATABASE_TEST_URL`, `HOMEOS_TEST_PROVIDERS`, and test telemetry/push settings are test-only and must never be configured in production.

## Hostinger deployment procedure

1. Provision an empty external PostgreSQL database. Record its TLS connection URI. Do not use a customer or test database.
2. In hPanel, choose **Websites → Add Website → Deploy Web App → Import Git Repository** and select `pradeep5849/Amj-homeos` on the approved main commit.
3. Select **Next.js** and Node.js **22.x**.
4. Add `DATABASE_URL`, `SESSION_SECRET`, and `NODE_ENV=production` in hPanel. Do not add test variables or provider credentials.
5. Select the repository script `npm run deploy:build` as the build command. It generates Prisma, applies checked-in migrations with `prisma migrate deploy`, and builds Next.js. If hPanel does not allow that script, run `DATABASE_URL='…' npx prisma migrate deploy` once from a trusted local checkout, then use `npm run build` in hPanel; never use `prisma migrate dev`.
6. Use `npm start` as the production start command. Do not hard-code `PORT` or weaken cookie settings.
7. After the first successful deployment, run the one-time bootstrap from a trusted local checkout with the production `DATABASE_URL` and the three `SUPER_ADMIN_*` variables: `npm ci && npx prisma generate && npm run bootstrap`. Do not run tests, seeds, or `prisma migrate dev` against this database. Remove the bootstrap variables when finished.
8. Open `https://<your-domain>/sign-in`, confirm `200`, sign in, and verify `/api/v1/auth/me` in the same browser session.
9. Attach a real domain and retain Hostinger HTTPS. Production cookies are `HttpOnly`, `Secure`, `SameSite=Lax`, and scoped to `/`; do not test production authentication over plain HTTP.
10. Configure recurring workers only after validating hPanel's custom cron command can enter the deployed Node.js working directory. Cron schedules are UTC in Hostinger's documented interface.

## Recurring workers

Each command is an idempotent, private, run-once worker. Only one cron invocation of a command should run at a time.

| Suggested UTC cadence | Command | Purpose |
|---|---|---|
| Every minute | `npm run scheduler:once` | Claims and runs due timers and Automation schedules. Required for timely schedules. |
| Every 5 minutes | `npm run health:once` | Marks previously observed Devices offline after the existing 15-minute stale threshold. |
| Hourly | `npm run telemetry:aggregate` | Upserts current Home-timezone daily energy aggregates. |
| Daily | `npm run telemetry:retention` | Deletes up to 1,000 raw telemetry rows older than 90 days. |
| Hourly | `npm run invitations:expire` | Marks pending invitations expired after their existing seven-day TTL. |
| Daily | `npm run audit:retention` | Deletes bounded security/Home activity batches older than 365 days. |

Hostinger documents custom cron commands on web/cloud plans, but deployed paths and Node command availability must be confirmed in the account. If hPanel cannot run these commands in the Node application environment, use an external scheduler or a VPS. The web application can be opened for a temporary UI test without workers, but timers, schedules, health transitions, aggregation, and retention will not run on time.

## Live mobile test checklist

- [ ] Open the HTTPS URL at approximately 360 px and 390 px widths; confirm no horizontal page overflow.
- [ ] Sign in, refresh, open `/dashboard` directly, and confirm authentication persists.
- [ ] Sign out, refresh `/dashboard`, and confirm redirect to sign-in.
- [ ] Check Home overview and useful empty/unavailable states.
- [ ] Switch between accessible Homes and confirm names, Rooms, and Devices change without unrelated data.
- [ ] Open Rooms and confirm the Home → Room → Device relationship.
- [ ] Open Devices; verify only supported logical controls appear and physical transport remains `Not configured`.
- [ ] Run an enabled Scene and confirm disabled Scenes cannot run.
- [ ] Review Automations and human-readable triggers/actions.
- [ ] Create/cancel a timer or schedule only after the scheduler cron is active; otherwise confirm it remains honestly pending.
- [ ] Confirm missing Energy data says unavailable rather than zero.
- [ ] Check Presence states and confirm no precise coordinates/history are displayed.
- [ ] Review Notifications, unread count, mark read, and mark all read.
- [ ] As an OWNER, review members and pending invitations; verify the raw invitation token appears only in the one-time creation response.
- [ ] Change password only with a disposable test account; verify other sessions are revoked as documented.
- [ ] Review current/other sessions and revoke another disposable session.
- [ ] Test a MEMBER account and confirm management actions are absent and direct management requests remain denied.
- [ ] Exercise long names/emails, empty Homes, unavailable energy, unknown health, and invalid form errors.

## Provider status

Wi-Fi/BLE, Zigbee, Tuya, FCM, APNs, Web Push, Android/iOS background location, email, SMS, and WhatsApp remain `NOT_CONFIGURED`. This deployment adds no Home Assistant, MQTT, Zigbee2MQTT, provider credential, or fabricated physical success.
